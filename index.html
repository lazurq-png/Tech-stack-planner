Tech Stack Planner

Answer one question at a time to choose the technologies for a game or website. Each suggestion is based on your earlier answers, what works best for them, and what is easiest to develop with.

Part 1

Choose your project

Answer one question at a time. Each answer decides what comes next, and later questions stay hidden until the ones before them are answered. Changing an answer clears the choices after it. Your answers stay in this browser.

How the questions are ordered

Every route follows the same eight stages. A stage that doesn't apply is skipped, and the page tells you why.

  1. Product: game or website.
  2. Requirements: what it must do, such as login, selling or online play. No technology yet.
  3. Approach: use an existing platform or engine, or build your own. For a game, this includes its language.
  4. Backend: language, then framework, because every later library depends on them.
  5. Interface: what users see, then how it talks to the backend.
  6. Data: saved games for a game. For a server, the database, then the library that uses it, then how its structure changes.
  7. Services: login, admin, payments and game features such as achievements and crash reports, which all build on your data.
  8. Delivery: hosting and stores, last because they must run everything above.

Three rules set the order: requirements come before technology, a choice can only limit the questions after it, and the choices hardest to change come first.

Your ADR drafts

How to record a decision

An Architecture Decision Record (ADR) is a short file explaining one technical decision and why you made it. Future you can then see what was considered, instead of guessing from the code. A common location is docs/adr/, with one numbered Markdown file per decision.

docs/adr/0001-use-postgresql.md

# ADR 0001: Use PostgreSQL as the main database

Status: Accepted
Date: 2026-11-02

## Context
The app stores users, roles and related business data.

## Options considered
PostgreSQL, MySQL, SQL Server, MongoDB and H2.

## Decision
Use PostgreSQL.

## Consequences
We get strong relational features and wide hosting support.
Production needs managed backups and connection pooling.
# ADR 0001: ...
The number gives a permanent ID, and the title states the decision.
Status
Usually Proposed, Accepted, Deprecated or Superseded.
Date
When the decision was made, which helps you judge whether its reasoning is out of date.
Context
The problem and constraints at the time.
Options considered
What you compared. You can adapt the pros and cons below.
Decision
The choice, stated directly.
Consequences
The benefits and costs you're accepting.

Don't rewrite an accepted ADR when you change your mind. Add a new one and mark the old one as superseded. Each of your answers has a draft below, ready to copy and finish.

Four language differences explain most of the code below:

  • Object variables are references. Task t points at an object rather than containing it, so two variables can refer to the same object.
  • Memory is garbage collected. There's new, but no delete and no destructors to rely on.
  • Methods can be overridden by default. Non-static, non-private, non-final methods can be replaced in a subclass. That's what lets test libraries swap them for fakes.
  • Arguments are always passed by value. For objects, the value copied is the reference, so a method can change the object but not your variable.

Spring concepts

Bean
An object that Spring creates and owns. By default there's one per class, like a singleton.
Application context
The container that holds all the beans.
Dependency injection
Instead of each class creating what it needs, Spring finds what each constructor asks for, then creates and connects the objects in the right order.
Component scan
Spring searches your package for classes with marker annotations and makes them beans.
Auto-configuration
Spring Boot checks which libraries are on the classpath and sets up sensible defaults.
Starter
A dependency that brings in a group of related libraries.
Thread safety
Tomcat handles requests on a thread pool, and they all share the same controller object. Don't store per-request data in a controller's fields, because other requests would see it.
HTTP request
  → Tomcat             embedded web server
  → DispatcherServlet  finds the method matching the URL
  → @RestController    handles HTTP input and status codes
  → @Service           business logic
  → Repository         database access
  ← Jackson converts the returned object to JSON

Set up your machine

The commands use a Unix-style shell. That means the terminal on macOS or Linux, and Git Bash or WSL on Windows.

Step 1: Install JDK 25

The JDK contains the compiler (javac) and the runtime (java). Download Temurin, a free OpenJDK build, from adoptium.net and run the installer for your system. Choose the options to set JAVA_HOME and add Java to your PATH if the installer offers them.

If you can't run installers, download the archive version instead and extract it anywhere. Then set these two environment variables yourself:

JAVA_HOME
The extracted folder, which is the one above bin. Tools use this to find the JDK.
PATH
Add that folder's bin folder, so you can type java anywhere.

Programs read these variables when they start, so reopen your terminals and editor afterward. Then check the install. Both commands should report version 25:

java -version
javac -version

Step 5: First endpoint

src/main/java/com/example/demo/HelloController.java

package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

	@GetMapping("/hello")
	public String hello(@RequestParam(defaultValue = "world") String name) {
		return "Hello, " + name + "!";
	}

}
@RestController
Makes this a bean and writes each method's return value to the HTTP response.
@GetMapping("/hello")
Routes GET /hello to this method. Think of a route table built automatically at startup.
public String hello(...)
Returns a string. Java strings are immutable objects, so concatenation creates a new one.
@RequestParam(defaultValue = "world")
Fills the parameter from ?name=..., or uses the default.
String name
Spring needs this parameter name at runtime to match ?name=. The compiler normally discards parameter names, but the parent POM tells javac to keep them.
return "Hello, " + name + "!";
Builds the response text.

Start the app with ./mvnw spring-boot:run, then in a second terminal run:

curl "http://localhost:8080/hello?name=Spring"

You should see Hello, Spring!. The quotes stop the shell from treating ? specially.

A profile is a named set of settings, chosen when the app starts.

src/main/resources/application-dev.properties

spring.jpa.show-sql=true
Prints the SQL that Hibernate runs. It only affects JPA, so with other data access choices use logging.level.org.springframework.jdbc=DEBUG or your library's own logging.

./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

  1. Command-line arguments
  2. Environment variables
  3. application-{profile}.properties
  4. application.properties

This sets an environment variable for one command. Spring maps SERVER_PORT to server.port. Use environment variables for passwords and other secrets, to keep them out of Git.

What to learn next

  1. Consistent error responses: use @RestControllerAdvice to handle errors in one place, a bit like a central catch block for all controllers.
  2. A real database: install PostgreSQL. Add org.postgresql:postgresql with runtime scope and point spring.datasource.url at it. Tables aren't created automatically there, so use spring-boot-starter-flyway and org.flywaydb:flyway-database-postgresql to manage them.
  3. Your ADRs: finish the drafts in Part 1 and commit them to docs/adr/.
